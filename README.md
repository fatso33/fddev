# Flight Deck PWA

The tablet/mobile avionics touchscreen companion app for MSFS 2024. Plain static HTML/CSS/JS — no build step.

- **Radio Stack**: Active/Standby tuning for COM1, COM2, NAV1, NAV2 with presets.
- **Autopilot Matrix**: AP Master, Auto-Throttle, Flight Director, Heading Bug, Altitude, VS wheel, NAV/APR/BC holds, Flaps/Spoilers.
- **Lighting Systems**: External and internal lighting controls.
- **Dual-Orientation Grid Engine**: Declarative grid layout with portrait/landscape mirroring and local persistence.
- **App Profiles**: named sets of page layouts (top-right badge), synced with [Flight Deck PC Bridge](../pc-bridge) over WebSocket (`js/core/SimBridge.js`, configurable in-app under Settings). Distinct from PC Bridge's own "SimVar Binding Profile" (Deck-Event-to-SimConnect mapping), which this app never edits directly. `SimBridge.js` auto-upgrades this connection to `wss://` whenever the PWA itself is loaded over `https://` (e.g. hosted on GitHub Pages) — browsers block a plain `ws://` connection from a secure page outright, so PC Bridge has to speak real TLS for that case; it does, via a self-signed certificate (see [pc-bridge's README](../pc-bridge#network--tls)). Each phone/tablet needs a one-time step the first time it connects: Settings shows an "Open Trust Page" link (`https://<PC's LAN IP>:<port>/api/health`) to accept the certificate warning, since a WebSocket handshake can't surface that prompt itself. Editing a page layout while a shipped default App Profile is active auto-forks a "Custom" App Profile that stores only the overridden pages — every other page keeps resolving from the default — and a page can be reverted back to its default independently of any other edited page in the same fork (`js/models/Profile.js`'s `parentProfileId`/`hydrateInheritedPages()`, `js/app.js`'s `ensureEditableProfile()`/`handleRevertPageToDefault()`; see `../CHANGELOG.md`'s 2026-08-27 entry). Custom (non-shipped) pages can be added from the nav menu and are tracked per-profile the same way.
- **Community Deck Events Packs** (Settings page, `js/ui/SettingsView.js`): import a shareable JSON pack of extra logical binding-name suggestions (e.g. for a specific G1000/G3000 aircraft), or export the custom names your own installed widgets already use so you can hand them to someone else. Purely an authoring-time convenience for `js/ui/PropertyInspector.js`'s binding pickers — see `js/core/deckEventPacks.js` and the root [README](../README.md#shared-keeping-the-widget-component-library-in-sync).
- **Keep Screen Awake** (`js/core/WakeLockManager.js`): uses the Screen Wake Lock API to stop the device display from timing out while the app is open — on by default, toggleable from the nav menu ("Keep Screen Awake", next to Night Cockpit). Re-acquires automatically on `visibilitychange` back to visible, since the browser force-releases the lock whenever the page is hidden (spec behavior, not a bug). No-ops silently — toggle shown disabled with an explanatory tooltip — on browsers/contexts without support (e.g. non-HTTPS origins).
- **Night Cockpit (dark/light theme)** (`js/app.js`, nav menu; dark by default): flips `<html data-theme>`, which the app chrome's CSS custom properties (`css/main.css`) already redefine per theme. As of 2026-08-27, custom widgets react too — every mounted widget's literal authored colors and gradients (`style.background`/`border`/`typography.color`) are re-derived for the new theme (`shared/widgets/components/ThemeColor.js`, hue-preserving HSL remap) and the active page is fully re-rendered on toggle, since those colors are resolved once per render rather than reactively. See the root [`../CHANGELOG.md`](../CHANGELOG.md)'s 2026-08-27 entry.

## Run locally
Any static file server works, e.g.:
```bash
npx serve .
```
Then open the printed URL. It's a PWA — install it from the browser for a standalone/fullscreen experience.

## Deploy to GitHub Pages
Set the repo's Pages source to this folder (or publish it as the root of a dedicated `gh-pages` branch / repo). No build step is required — just the contents of this directory.

## Widget components
`js/widgets/components/`, `js/widgets/definitions/`, `js/core/SecurityValidator.js`, `js/core/deckEvents.js`, `js/core/widgetVarExtractor.js`, and `js/core/deckEventPacks.js` are synced from [`../shared/`](../shared) — see the root [README](../README.md) before editing them directly. Widget rendering follows the Flight Deck Widget Standard (FDWS), current version v1.23 (see [`../docs/FlightDeck-Widget-Standard-v1.23.md`](../docs/FlightDeck-Widget-Standard-v1.23.md), a delta spec over [v1.22](../docs/FlightDeck-Widget-Standard-v1.22.md), [v1.21](../docs/FlightDeck-Widget-Standard-v1.21.md), [v1.20](../docs/FlightDeck-Widget-Standard-v1.20.md), [v1.19](../docs/FlightDeck-Widget-Standard-v1.19.md), [v1.18](../docs/FlightDeck-Widget-Standard-v1.18.md), [v1.17](../docs/FlightDeck-Widget-Standard-v1.17.md), [v1.16](../docs/FlightDeck-Widget-Standard-v1.16.md), [v1.15](../docs/FlightDeck-Widget-Standard-v1.15.md), [v1.14](../docs/FlightDeck-Widget-Standard-v1.14.md), [v1.13](../docs/FlightDeck-Widget-Standard-v1.13.md), [v1.12](../docs/FlightDeck-Widget-Standard-v1.12.md), [v1.11](../docs/FlightDeck-Widget-Standard-v1.11.md), [v1.10](../docs/FlightDeck-Widget-Standard-v1.10.md), [v1.9](../docs/FlightDeck-Widget-Standard-v1.9.md), [v1.8](../docs/FlightDeck-Widget-Standard-v1.8.md), [v1.7](../docs/FlightDeck-Widget-Standard-v1.7.md), [v1.6](../docs/FlightDeck-Widget-Standard-v1.6.md), [v1.5](../docs/FlightDeck-Widget-Standard-v1.5.md), [v1.4](../docs/FlightDeck-Widget-Standard-v1.4.md), [v1.3](../docs/FlightDeck-Widget-Standard-v1.3.md), and [v1.2](../docs/FlightDeck-Widget-Standard-v1.2.md)); `shared/widgets/` is at full v1.2 conformance, plus v1.4's `revision` field validation and v1.5's `core.gauge.props.compose` (`SecurityValidator.validateFDWSDefinition()`, `GaugeComponent.js`). See the root [`../README.md`](../README.md) and [`../CHANGELOG.md`](../CHANGELOG.md) for what v1.6 through v1.16 each added. v1.17 adds `core.divider` — a grid-snapped separator line, rendered by `js/widgets/components/DividerComponent.js` — and a generic `style.border.style` (solid/dashed/dotted) any component's border can use. v1.18 adds manual per-theme styling — a widget-root `baseTheme`/`themeMode` plus a component/widget-root `style.themeOverride`, resolved by `CompositeWidget.js`'s `getThemeConfig()` and `js/widgets/components/ThemeColor.js`'s new `resolveThemedColor()`/`resolveThemedColors()`/`resolveThemedBackground()`; every pre-v1.18 widget (no `baseTheme`/`themeMode`/`themeOverride`) renders exactly as before.

**v1.3 Widget Popovers are implemented — outside `shared/`, in this app's own widget tree.** `js/widgets/components/WidgetPopoverModal.js` mounts a `kind: "popover"` widget definition as a modal, driven by a host widget's `core.openWidgetPopover` interaction (`CompositeWidget.js`); `WidgetRegistry.js` resolves `popoverWidgetId` to a saved definition, and `WidgetDrawer.js` excludes `kind: "popover"` widgets from the "place a widget on this page" picker per spec. This file isn't (and shouldn't be) synced from `shared/widgets/components/` — it has to construct a real `CompositeWidget` around the popover definition, which only this app's runtime can do; Widget Studio has its own independent implementation built around its `MockWidgetHost` instead, for live-preview rather than production rendering.

**v1.19 (2026-08-28): a widget's popover(s) install together with it.** `WidgetRegistry.installDefinition()` and `StorageManager.importWidgetDefinitionJSON()` both unpack an incoming definition's `popovers` array — each entry installed exactly as if it had been imported on its own — before persisting the host without that array; the "Install .fdwidget" flow in `js/ui/WidgetDrawer.js` reports how many bundled popovers came along. Exporting a widget (`StorageManager.exportWidgetDefinitionJSON()`) does the reverse: it collects the widget's own referenced `popoverWidgetId`s and inlines whichever are installed locally. A same-day follow-up fixed two real bugs found live-testing this: `WidgetPopoverModal.js`'s modal chrome was hardcoded dark regardless of `[data-theme]` (now uses the same theme-aware CSS custom properties the app chrome does), and `core.label`'s `update()` treated an intentionally-empty `props.text` as falsy and rendered the component's Studio-authoring `label` metadata instead — see the root `CHANGELOG.md` for the full live-repro writeup.

**`js/core/SimBridge.js` telemetry-envelope bug (fixed 2026-08-28→29 verification pass):** found while testing the FDWS v1.20 instrument components live against a real MSFS 2024 session via PC Bridge. The telemetry handler's `{ ...packet.data, ...packet }` merge re-spread the whole message envelope (`type`, `profile`, the original nested `data` object) back on top of the already-flattened simvar values, so every frame with a `.data` wrapper queued three bogus "simvar" entries into `EventBus.ingestTelemetry()` alongside the real readings — noisy, but real data was never lost (a valid `.data` payload still merged in correctly). Fixed to `packet.data || packet`, confirmed live: a frame with no real values yet now correctly queues as `{}` instead of `{ type: 'simData', profile: '...', data: {} }`.

**v1.21/v1.22 (2026-08-29): local-state array persistence, including a session-only mode.** `CompositeWidget.js`'s `setLocalState()`/`initLocalState()` previously ignored `persist` entirely for `type: "array"` state — v1.21 loosened that to only reject the combination with `syncFrom` set (a live-synced array still can't persist; a local-only one now can, same as any scalar). v1.22 then added a third `persist` value, `"session"`: written into the same in-memory widget-instance config `true` uses (so it survives `js/app.js`'s `switchPage()` destroying and rebuilding widget instances on page navigation), but the `WIDGET_CONFIG_CHANGED` event now carries a `sessionOnly` flag that makes `app.js`'s handler skip the `storage.saveProfile()` durable write — so it resets to `default` the next time the app is actually relaunched, rather than persisting forever. Motivated by the COM1/COM2 collapsible radio widget's presets, which should differ flight to flight rather than silently carrying over. See `../CHANGELOG.md` and the v1.21/v1.22 specs for the full writeups.

**PC Bridge sync-loop bug (fixed 2026-08-29, not a `flight-deck-pwa` code change):** PC Bridge's `saveUserPreset()` was unconditionally re-stamping `updatedAt` on every push from this app, so this app's own local copy (still holding its original timestamp) was always seen as "missing" on the very next sync check — an unbounded push/pull cycle, not paced by any timer, just network round-trip latency (~1s/cycle observed live). This app's own `StorageManager.js`'s `saveProfile()` already handled this correctly (only stamps `updatedAt` if not already set); PC Bridge didn't match it. See `../pc-bridge/README.md` and `../CHANGELOG.md`.

**Popover Save race with masked `core.input` (fixed 2026-08-29):** found live-testing the COM1/COM2 collapsible radio widget's preset popover — typing a frequency and pressing Save committed an empty/stale value instead of what was typed. Root cause: a masked `core.input` (FDWS v1.11) only writes its typed value into local state on a `blur`/`change` event, and the popover's Save button (`core.commitToHost`) reads that local-state value at tap-time — if the field hadn't already lost focus, Save read the value it had *before* the user's edit landed. Fixed at the shared-code level: `InputComponent.js` gained `flushPendingEdit()` (commits a dirty pending edit immediately, independent of any DOM event), and `InteractionDispatcher.js`'s `runInteraction()` now calls `host.flushPendingEdits()` before any `tap`/`longpress` action runs — `CompositeWidget.js`'s `handleInteraction()` wires this to its own `componentRenderers`. Verified end-to-end by mounting the real widget definition and driving its DOM: typing digits via `input` events then tapping Save with zero prior blur now correctly commits and re-renders the bound label. Rejected/out-of-range input (e.g. `"12"`, below `FREQ_COM`'s 118.000 minimum) is unaffected — the format's existing reject-and-revert validation (v1.11) still runs first, so an invalid edit never reaches local state regardless of when it's flushed.

**`core.input` no longer lets a mobile keyboard "Next" into an adjacent field (fixed 2026-08-29):** reported on the same widget — with COM2 visible, typing into COM1 STBY and pressing the on-screen keyboard's action key moved focus to COM2 STBY instead of dismissing the keyboard. Neither app has any explicit next-field-navigation code (no `<form>`, nothing in `CompositeWidget.js`); this was the keyboard itself inferring a "Next" action from a nearby focusable input. Fixed by setting `enterKeyHint = 'done'` on every rendered `core.input` (`InputComponent.js`), matching the existing physical-Enter-key handler's own `inputEl.blur()` behavior.

**PC Bridge sync loop, round two (fixed 2026-08-29, not a `flight-deck-pwa` code change):** testing the above surfaced the exact same "kept syncing continuously" symptom, but for a different widget (`com.flightdeck.throttle`) and a genuinely different cause — a duplicate on-disk widget file for that id in PC Bridge's `widgets/` folder, one copy missing `updatedAt`, feeding an unstable fallback timestamp into the sync comparison. See [`../pc-bridge/README.md`](../pc-bridge/README.md) for PC Bridge's fix. This app's `SimBridge.js` gained a 2-second debounce on `checkAndSyncPresets()` as a backstop regardless of root cause, since the broadcast-triggered resync (`USER_PRESETS_UPDATED` → `checkAndSyncPresets()`) turns ANY transient server-side inconsistency into an unbounded loop unless something limits how often it can re-fire.

**FDWS v1.23 (2026-08-29): `interactions[].condition`.** Reported on the same widget: tapping an *unset* preset button dispatched an invalid `0.000` frequency instead of doing nothing. `visibleWhen` couldn't fix this without also hiding the button's long-press-to-set affordance, so a new optional `interactions[].condition` (reusing `visibleWhen`'s own condition grammar) now gates whether a specific interaction's action fires at all — evaluated in the shared `InteractionDispatcher.js`'s `runInteraction()`, so no per-app runtime change was needed. This is authored entirely in Widget Studio's interaction editor (a new "Only Run If" section) — the COM12 combo widget itself wasn't edited as part of this fix, since the whole point was to make the fix something the widget's author applies through Studio, not something baked into the runtime unconditionally. See `../CHANGELOG.md` and the v1.23 spec for the full writeup.

**Installed-PWA auto-rotation ignoring the Android rotation lock (fixed 2026-08-30):** reported after installing on a second phone (Pixel 7) — the *installed* app auto-rotated even with Android's own auto-rotate setting disabled, while a plain browser tab at the same URL correctly respected the lock on both phones, and the installed app on the original test phone (Pixel 10) also respected it. `manifest.json`'s `display_override` listed unused `"fullscreen"` mode ahead of `"standalone"` — Chrome translates the web manifest's `orientation` field into a native `android:screenOrientation` attribute on the installed app's wrapper APK at install time (a step a browser tab never goes through), and true fullscreen mode is documented to hand full orientation control to the sensor regardless of the system lock. Removed `"fullscreen"` from the list since nothing here uses it. The actual fix on that specific device turned out to be updating Chrome itself (an older build's `orientation:"any"` → native-`screenOrientation` translation was buggy) — the manifest cleanup is kept regardless since it served no purpose and remains a plausible contributor on other Chrome/Android builds.

**Virtual Yoke pitch inverted in one of its two landscape holds (fixed 2026-08-30):** rotating the phone counterclockwise into landscape gave correct pitch/roll; rotating clockwise into landscape instead gave inverted pitch, with roll still correct in both. Pitch is decomposed from rotation about the phone's own physical long axis, which reverses real-world direction between the two landscape holds even though the actual nose-up/nose-down gesture is identical; roll is decomposed from rotation about the screen-normal axis, which doesn't change direction between the holds, so it never needed correction. `VirtualYokeEngine.js` gained `_getScreenOrientationAngle()` (reads `screen.orientation.angle`, falling back to legacy `window.orientation`, then `90`) and now flips pitch's sign only when the angle is `270` (landscape-secondary). Confirmed fixed on real hardware — see `../docs/Virtual-Yoke-Page.md`'s "Landscape-primary vs. landscape-secondary pitch inversion" section and `../CHANGELOG.md` for the full writeup.

**Auto-compact turned off by default; edit toolbar moved to the top (2026-08-30):** `js/core/LayoutEngine.js`'s `compactLayout()` — which ran on nearly every render/add/remove/move, pulling every widget but the one just moved up to close any gap above it — is now split into `normalizeLayout()` (coordinate cleanup only, used by every automatic path) and `compactLayout()` (the actual gap-closing pass, now only run by a new explicit "Compact" button in the edit toolbar). The toolbar itself (`js/ui/EditToolbar.js`) moved from a fixed bottom bar to a top bar that takes over the app header's own flex slot while editing (hides `.top-bar`, shows the toolbar in its place) — no overlap/padding math needed since it's normal document flow, not `position: fixed`; this also fixed a real bug where 5 buttons had been silently overflowing a 4-column CSS grid. All 6 buttons (5 existing + Compact) are icon+caption in one row. See `../CHANGELOG.md` for the full writeup.

**Fullscreen toggle to hide the mobile status bar (2026-08-30):** new `js/core/FullscreenManager.js` (mirrors the existing `WakeLockManager.js` pattern) wraps the standard Fullscreen API (`requestFullscreen()`/`exitFullscreen()`) — deliberately not the manifest's `display:"fullscreen"` mode, since that goes through the same Android WebAPK-manifest-translation layer that had the rotation-lock bug above, and would need every device to reinstall the app to pick up a future change. A new toggle in the menu (alongside Night Cockpit/Keep Screen Awake) persists the preference to `localStorage`; since browsers never resume fullscreen automatically after a reload, it re-requests on the user's next tap if left enabled. A same-day follow-up added the manager's own `onEnter` callback, wired to the app's own toast with correct instructions — Android's system-level "press Back to exit full screen" toast can't be edited or suppressed from the page and is inaccurate here (no in-app Back target). Confirmed working on real hardware (Pixel 7 and Pixel 10 Pro XL); the Fullscreen API is blocked entirely in the sandboxed dev browser, so this could only be verified live. See `../CHANGELOG.md`.

**Menu button repositioned and doubles as connection status (2026-08-30):** the two separate PC Bridge/Simulator status dots (`#sim-status`/`#sim-connect-status`) are gone — that information is now shown by the menu button itself, which also moved off dead-center (`.garmin-menu-btn` was absolutely centered) to the left, since a centered button collides with a phone's camera cutout now that Fullscreen mode can remove the status bar's own vertical clearance above it. `app.js`'s `BRIDGE_STATUS`/`SIM_STATUS` handlers now track both flags and toggle `.bridge-connected`/`.sim-connected` on the button (new `--accent-magenta` token in `css/main.css`, both themes) — neutral with no connection, cyan once PC Bridge connects, magenta once the simulator connects (taking priority, since it implies the bridge is connected too). Verified live: each connection event independently produced the correct color transition. See `../CHANGELOG.md`.

**Menu button and App Profile badge become real corner widgets (2026-08-30, same day):** the fixed `.top-bar` header is gone — the menu toggle (`js/widgets/MenuToggleWidget.js`, fixed 3×2) and App Profile badge (`js/widgets/AppProfileWidget.js`, renamed from `AircraftBadgeWidget` — "aircraft badge" no longer described its function, fixed 5×2) are now real `BaseWidget` instances floated directly over the real page grid's own top-left/top-right cells via a new `.fd-corner-overlay` (`css/grid.css`, `position: sticky; height: 0; overflow: visible`), so the space between them is genuine, addable, draggable page-grid space rather than dead header chrome. Both are rebuilt fresh on every `js/app.js`'s `renderActivePage()` call (all branches, including Settings and the Virtual Yoke rotate-prompt) instead of persisting outside it — neither carries SimVar bindings, so this is cheap and avoids needing a second parallel widget lifecycle. Sizes are authored against the same 20/44-col mobile reference every other widget's `defaultLayout` uses (`app.js`'s `getCornerWidgetLayouts()`), and their cells are reserved (never persisted to `Profile`/`Page`) across every collision-aware operation — add, drag, compact, mirror — via new `resolveWithReservedCorners()`/`resolveListWithReservedCorners()` helpers, added after a first pass naively splicing them into `LayoutEngine.resolveLayoutWithPushDown()`'s widget list discovered that function always keeps whichever id you pass it as "moving" fixed and pushes everything else — including the corners — out of the way instead. A same-day follow-up fixed the corner widgets visually bleeding into the widget row below them: `.fd-widget`'s existing `min-height: 44px` touch-target floor exceeded their 2-row grid allocation (39px in mobile landscape), and CSS Grid doesn't grow a track to fit an oversized item, so the corner widget simply overflowed its cell — fixed with a `min-height: 0` override scoped to the two corner widgets' ids. While in page-edit mode, the menu widget also shows a pencil icon and toggles the edit toolbar's visibility instead of opening the nav dropdown (`FlightDeckApp.toggleEditToolbarVisibility()`), since the toolbar can otherwise cover the same rows the corner widgets and any real widget placed between them occupy. See `../CHANGELOG.md` for the full writeup, including the discarded first implementation (a separate pinned strip, which didn't actually free the space for real widgets).

**Corner widgets get a state-matched accent (same day):** `.garmin-menu-btn`'s border-color and a new inset floor-line `box-shadow` both use `currentColor` instead of a fixed accent, so they automatically track whichever color the existing `.bridge-connected`/`.sim-connected` classes set on the button (white at rest, cyan once PC Bridge connects, magenta once the simulator connects) — CSS-only, `css/main.css`, no JS change. `.aircraft-badge` moved from `--accent-cyan` to a fixed `--accent-green` for its text, border, and matching floor line, independent of connection state (magenta initially, swapped to green per a same-session follow-up). Mocked up as an Artifact (six on-theme options) before implementing; user picked a border+floor-line combo with this state-matching refinement. See `../CHANGELOG.md`.

**Corner widgets get curved-corner clearance in Fullscreen mode (same day):** with the status bar hidden, the two corner widgets sit flush against the true screen edges, where a curved-corner phone (Pixel 10 Pro XL) visibly clips them. Rather than widening each widget's grid footprint (which would permanently cost placeable space between the two corners, even on devices without curved corners), added two rules scoped to the standard `:fullscreen` pseudo-class in `css/main.css`: `.garmin-menu-btn` gets extra `padding-left`, `.aircraft-badge` gets extra `padding-right`, each `calc(existing + max(14px, env(safe-area-inset-*, 0px)))` — `env(safe-area-inset-*)` alone isn't reliable for corner rounding the way it is for notches, hence the fixed 14px floor. Only the button/badge's own inner content shifts; the widget's grid cell and `app.js`'s reserved-corner collision math are untouched, so real widgets placed between the corners are unaffected. Verified the rule loads correctly and leaves non-fullscreen padding unchanged; real curved-corner clearance needs on-device confirmation, since the Fullscreen API is blocked for non-trusted-gesture calls in the sandboxed dev browser. See `../CHANGELOG.md`.
